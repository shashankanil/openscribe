# Phone Link: Android companion

The Android app pairs with OpenScribe on the Mac over the local network. It does two things:

1. **Clipboard sync.** Text copied on either device can be sent to the other.
2. **Press-to-talk mic passthrough.** Hold a button on the phone, speak (or whisper) into it, and the Mac
   runs its normal dictation pipeline: transcribe, clean up, and paste into the focused Mac app. The
   Flowbar animates with the phone's audio exactly as it does for the Mac microphone.

The phone is only a microphone and a clipboard. Transcription, cleanup, the dictionary, snippets and
API keys all stay on the Mac. The phone stores no provider keys.

## Local network first, cloud when away

- Press-to-talk usually happens next to the laptop, so the phone tries the local network first: no account, no
  relay latency, and audio never leaves the network.
- When the phone can't reach the Mac (another network, mobile data), it falls back to the OpenScribe Cloud relay
  if the Mac is signed in with Google. The frames are the same end-to-end encrypted frames either way.
- Images go through R2 because they're too big for the link. See "OpenScribe Cloud: relay and images".

## Platform constraints that shape the UX

| Constraint | Consequence |
| --- | --- |
| Android 10+ blocks clipboard **reads** by background apps (only the foreground app or the default keyboard can read). | Phone → Mac is an explicit action: the in-app **Send clipboard** button, the **Send clipboard** Quick Settings tile (opens a transparent activity that reads on focus), and the system **Share → OpenScribe** sheet. Fully automatic phone → Mac needs an OpenScribe keyboard (phase 3). |
| Android allows clipboard **writes** from a foreground service. | Mac → phone is automatic while the link is connected. |
| Android 14 requires foreground service types, and a `microphone` service can start only while the app is visible. | The connection runs in a `connectedDevice` foreground service. Talking happens from the visible app, or from the overlay activity a Quick Settings tile opens. |
| macOS has no clipboard-change notification. | The Mac polls `NSPasteboard.changeCount` twice a second. It skips items marked `org.nspasteboard.TransientType`, `ConcealedType` or `AutoGeneratedType` (password managers set these), and OpenScribe's own paste-injection writes, which are now marked transient. |
| macOS 15 asks for Local Network access. | `NSLocalNetworkUsageDescription` and `NSBonjourServices` are in `AppInfo.plist`. The prompt appears the first time Phone Link is turned on. |
| Whispered speech is quiet, and the Mac discards captures whose peak level stays below speech level. | The phone applies **Whisper boost**: an adaptive gain of up to +24 dB with a noise gate and soft limiter, before sending. The phone records with `AudioSource.VOICE_RECOGNITION`, which has no system AGC. |

## Discovery and pairing

1. On the Mac: **Phone** page → **Pair a phone**. The Mac creates a device slot with a random 32-byte
   secret and shows a QR code of the pairing link. A slot that never connects expires after 10 minutes.
2. On the phone: scan the QR code (or paste the link). The phone stores the link encrypted with an Android Keystore AES key, excluded from backup and device transfer.
3. The Mac advertises Bonjour service `_openscribe._tcp` with TXT record `id=<mac id>`. The phone finds it with
   `NsdManager` by matching `id`. If discovery finds nothing in 3 seconds, the phone tries the `h` hosts from the link.
4. Removing a phone on the Mac deletes its secret, and the phone can no longer connect.

Pairing link:

```
openscribe://link?v=1&mac=<mac id>&name=<Mac name>&device=<device slot id>&k=<secret, base64url, no padding>&h=<ip>,<ip>&p=<port>
```

## Transport

TCP, default port 47689 (the Mac falls back to any free port, and Bonjour reports it). Each frame is a
4-byte big-endian length followed by that many bytes. Frames over 1 MiB are a protocol error.

### Handshake

1. Phone → Mac, **plaintext** JSON frame:
   `{"t":"hello","v":1,"device":"<device slot id>","nonce":"<16 random bytes, base64url>"}`
2. Mac → phone, **plaintext** JSON frame:
   `{"t":"welcome","v":1,"mac":"<mac id>","nonce":"<16 random bytes, base64url>"}`
   or `{"t":"error","code":"unpaired"|"version"}`, then the Mac closes the connection.
3. Both sides derive two AES-256-GCM keys:
   `key = HKDF-SHA256(ikm = secret, salt = clientNonce ‖ serverNonce, info = "openscribe-link-v1 c2s" | "openscribe-link-v1 s2c", L = 32)`
4. Every later frame is encrypted. Frame payload = `ciphertext ‖ 16-byte tag`, with no AAD. The nonce is implicit:
   4 zero bytes then a 64-bit big-endian counter. Each direction counts from 0 and adds 1 per frame. A frame that
   fails to open ends the connection.
5. Phone → Mac (first encrypted frame): `{"t":"auth","name":"Pixel 8","app":"0.1.0"}`.
   Mac → phone: `{"t":"ready","name":"<Mac name>","clipboard":true}`.
   The phone proves it has the secret by encrypting `auth`; the Mac proves it by encrypting `ready`.

### Plaintext of encrypted frames

The first byte is the kind, and the rest is the body.

| Kind | Body |
| --- | --- |
| `0x01` message | UTF-8 JSON, with the type in `t`. Ignore unknown types and unknown fields. |
| `0x02` audio | 16 kHz mono PCM, signed 16-bit little-endian. Any length; the phone sends 40 ms (1280 bytes). |

### Messages

| Direction | Message | Meaning |
| --- | --- | --- |
| phone → Mac | `{"t":"ping"}` | Sent every 15 s. The Mac answers `{"t":"pong"}`. Either side drops a link that has been silent for 45 s. |
| both | `{"t":"clip","id":"<uuid>","text":"…"}` | Put this text on your clipboard. UTF-8, at most 256 KiB. The receiver answers `{"t":"clip_ack","id":"…"}`. |
| phone → Mac | `{"t":"talk_start","id":"<uuid>","rate":16000,"channels":1,"format":"pcm_s16le"}` | Start dictation with phone audio. Audio frames follow. |
| phone → Mac | `{"t":"talk_end","id":"…"}` | Released: finish and transcribe. |
| phone → Mac | `{"t":"talk_cancel","id":"…"}` | Discard the recording. |
| Mac → phone | `{"t":"talk_state","id":"…","state":"…","text":"…","error":"…","target":"Slack","pasted":true}` | `state` is `recording`, `transcribing`, `done` (with `text`), `discarded` (too short or silent), or `failed` (with `error`). `target` is the Mac app the text goes to, and `pasted` says whether it will be pasted there (otherwise it is only saved to Notes). Both are optional. |

If the link drops during a talk, the Mac treats it as `talk_end`: the audio received so far is transcribed,
and dictation recovery keeps it if transcription fails.

## Transcription on the phone

Sending audio to the Mac and transcribing it there adds a hop and, with a non-streaming model, waits until the
talk ends. When the Mac allows it (Phone page → **Transcribe on the phone**, on by default), the phone transcribes
while you speak and sends the Mac only text. Cleanup, the dictionary, snippets, spoken corrections and pasting stay
on the Mac.

### Speech settings (Mac → phone)

After `ready`, and whenever the transcription connection or the setting changes, the Mac sends:

    {"t":"speech","provider":"openRouter","url":"https://openrouter.ai/api/v1","model":"mistralai/voxtral-mini-transcribe",
     "key":"<transcription API key>","streaming":"openAI"|"mistral"|"deepgram"|"assemblyAI"|null,"terms":["OpenScribe",…]}

or `{"t":"speech"}` when the setting is off, there is no key, or the provider is one the phone can't use. Only the
**transcription** key is shared, never the writing key, and only with an authenticated, paired phone over the
encrypted link. `streaming` names the realtime transport (the Mac's `StreamingCapability`, same endpoints, query
parameters and auth as `Sources/OpenScribe/StreamingCapability.swift` and `RealtimeTranscription.swift`); `null`
means the phone uses the provider's file endpoint. `terms` are dictionary words to pass as hints, as the Mac does.

The phone stores this per Mac (encrypted with the Android Keystore, like the pairing) and deletes it on
`{"t":"speech"}`, when that Mac is forgotten, or when the Mac rejects the phone.

### Talking with phone transcription

    phone → Mac  {"t":"talk_start","id":"…","mode":"text"}
    phone → Mac  {"t":"talk_partial","id":"…","text":"<everything heard so far>"}   (repeated, at most ~5 per second)
    phone → Mac  {"t":"talk_text","id":"…","text":"<final transcript>"}             (replaces talk_end)
    phone → Mac  {"t":"talk_cancel","id":"…"}
    Mac → phone  talk_state as before: recording, transcribing (= writing it up), done, discarded, failed

The Mac shows partial text in the Flowbar while you talk, then runs the final text through the same pipeline as its
own dictation and pastes it into the focused app (chosen when the talk started). A `talk_text` with only whitespace is
`discarded`.

How the phone transcribes:

- **Streaming providers** (`streaming` set): one WebSocket for the talk, opened on press; audio frames go to the
  provider as they're recorded, and partial text goes to the Mac as it arrives.
- **Everything else**: the phone cuts the recording at natural pauses (about 600 ms of silence, or every 8 s at most)
  and uploads each piece to the file endpoint while you keep talking, several at once if needed. On release only the
  last short piece is left, so the text arrives about a second later. Pieces are joined in order.
- **If transcription on the phone fails** (bad key, provider down, no internet but LAN), the phone falls back to the
  audio path above: `talk_start` (mode omitted) with the recorded audio, then `talk_end`, so nothing said is lost.

## OpenScribe Cloud: relay and images

Everything above works on the local network with no account. Two features need **OpenScribe Cloud**, which
means the Mac is signed in with Google (Settings → Connect AI apps). Both are off otherwise:

- **Relay.** When the phone can't reach the Mac on the local network, it connects through the Worker instead.
- **Images on the clipboard.** Images are too big for the link, so they are stored briefly in R2.

The cloud never sees plaintext. Relay traffic is the same end-to-end encrypted frames as on the LAN. Images are
encrypted with a one-time key that travels only inside the encrypted link. The phone never signs in itself:
the Mac mints a **phone token** for it, tied to the same Google account, and revokes it when the phone is removed.

### Phone tokens

`POST /api/v1/link/devices` with the Mac's `Authorization: Bearer osk_…` and JSON `{"deviceId":"<pairing slot id>","name":"Pixel 8"}`
returns `{"token":"oslp_…"}`. Minting again for the same `deviceId` revokes the previous token. Only the token's SHA-256
is stored (D1 table `link_devices`). `DELETE /api/v1/link/devices/<deviceId>` with the Mac token revokes it.
Deleting the account removes every phone token and blob.

After `ready`, and whenever cloud access changes, the Mac sends the phone (over the encrypted link):
`{"t":"cloud","url":"https://openscribe-cloud.…","token":"oslp_…"}`, or `{"t":"cloud"}` when the Mac signs out or turns
cloud off. The phone stores this with the pairing.

### Relay

`GET /api/v1/link/relay/<room>` as a WebSocket upgrade, with `Authorization: Bearer osk_…` (role **mac**) or `Bearer oslp_…`
(role **phone**). `room` is 32 lowercase hex characters:

    room = hex(HKDF-SHA256(ikm = pairing secret, salt = empty, info = "openscribe-link-v1 room", L = 16))

The Worker routes the socket to a Durable Object named `<userId>:<room>`, so rooms are per account: knowing a room ID
doesn't let another account join it. Each room holds at most one socket per role, and a new socket replaces the old one
(the old one closes with code 4000).

- **Binary messages** are frames: each one carries exactly one frame payload from the Transport section, without the
  4-byte length prefix. They are forwarded to the other role, or dropped if it isn't connected. At most 1 MiB.
- **Text messages from the Worker** are `{"t":"peer","present":true|false}`, sent on connect and whenever the other role
  joins or leaves. The phone sends `hello` only after `present: true`. When the peer leaves, both sides end the
  session; the Mac keeps its socket open and waits for the next phone session.
- **Keepalive:** either side may send the text message `ping` every 30 s; the Worker answers `pong` without waking the
  Durable Object (hibernation auto-response).

The Mac keeps one relay socket open per paired phone while Phone Link is on and it is signed in. The phone tries the
local network first (NSD, then pairing hosts) and uses the relay only when that fails.

### Images

`PUT /api/v1/link/blobs` with either token, `Content-Type: application/octet-stream`, and the encrypted bytes as the body
(at most 10 MiB + 28 bytes) returns `{"id":"<uuid>","expiresAt":<epoch ms>}`. `GET /api/v1/link/blobs/<id>` with either
token of the same account returns the bytes. Blobs live at `link/<userId>/<id>` in the `openscribe-media` bucket. An R2
lifecycle rule deletes the `link/` prefix after 2 days, and reads of anything older return 404.

Blob encryption: a random 32-byte key and a random 12-byte nonce, AES-256-GCM, no AAD, and the blob is
`nonce ‖ ciphertext ‖ tag`. The sender uploads, then sends over the link:

    {"t":"clip","id":"<uuid>","kind":"image","mime":"image/png","blob":"<blob id>","key":"<key, base64url>","size":<plaintext bytes>}

A text clip has no `kind` (or `"kind":"text"`). Images over 10 MiB are re-encoded as JPEG, scaled down until they fit.
The receiver downloads, decrypts, and puts the image on its clipboard, then acks with `clip_ack` as usual.
